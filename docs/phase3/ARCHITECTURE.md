The deployed OTP fix is owner-reported; its exact source remains unchanged here. Original export/import/OTP manifests and legacy source remain unchanged. ## Dedicated assignments and lifecycle

One customer is assigned one actual Realtime Database **instance**, never a Firebase project/app/device. Original assigned_user_id UNIQUE already enforces one instance per customer. The v1 additive migration creates an immutable assignment ledger, resource verification overlay, actions/wizards, jobs, audit/outbox and bot-health tables; it copies all old assignments without changing users, accounts, sessions or database URLs. Triggers prevent release/reassignment/deletion of assigned instances and edits/deletes of ledger entries. There is no automated release or destructive cloud deletion API. A future release procedure must prove erasure/isolation and receive a separate review; this implementation intentionally cannot recycle assigned databases.

Imported entries begin VALIDATING (or DISABLED), retain every assignment and are not silently considered verified. Only verified, active, fresh AVAILABLE entries can be allocated, within BEGIN IMMEDIATE. Successful assignment becomes ASSIGNED, records ledger/audit and queues notification. Duplicate registration/renewal/status calls return the same assignment. Expiry denies access but does not free capacity. Renewed eligibility restores the existing assignment, subject to current verification and enablement. Disabled/ERROR instances block URL/gateway access and never silently become available. Enable requires explicit owner confirmation and fresh validation. Disable is local pool/backend access control, not Cloud's physical disable method; data is not deleted.

The overlay uses PROVISIONING/VALIDATING/AVAILABLE/ASSIGNED/DISABLED/ERROR semantics. Persisted creation jobs record INIT/REQUESTED phases, PROVISIONING/VALIDATING states and bounded retry/error/completion. Planned resources are jobs, not falsely counted as registered/ready pool instances. Existing active verified entries are revalidated in the background after 12 hours; verification expires after 24 hours. ERROR/DISABLED entries require explicit operator recovery; existing assignments are never moved. A stopped/unconfigured worker can therefore cause access to fail closed pending revalidation.

## Owner and callbacks

Every privileged operation requires private chat, matching sender/chat IDs, active backend role owner and the linked canonical NemesisOwner account. Telegram usernames are not authorization. Forwards and foreign/inline callback messages are refused. Callbacks carry only a random opaque token whose hash, actor, originating message ID, action, payload, expiry (180 seconds) and consumption are stored server-side. They are single-use under a serialized transaction. Final operations recheck owner, customer eligibility, assignment, request revision and validation result hash; stale registration or disable confirmations are refused. Rate limit: 30 successful administrative interactions per minute. Guided inputs expire after ten minutes. No documents/private-key JSON are downloaded or accepted as credentials.

Cloud operations run on a background worker, not the polling dispatcher. Polling includes callback_query; errors are isolated per update and offsets continue. Original registration/linking commands and 403 recovery remain. Poll success records a non-personal heartbeat for deployment validation. Notifications use a durable, leased, bounded-retry outbox. Delivery is at-least-once (duplicates are possible after ambiguous Telegram timeouts); callback/revision checks prevent duplicate decisions. Failed messages become FAILED; original pending requests remain visible for manual review. A low-pool alert is deduplicated per hour; it never provisions resources automatically.

## Provisioning and access boundaries

A configured alias binds project ID, project number, region, service identity, reviewed project-policy fingerprint and instance cap. Only us-central1, europe-west1 and asia-southeast1 URL formats are supported. The official RTDB v1beta API discovery was inspected; create returns a DatabaseInstance, not an invented long-running operation. Bounded consistent GET checks recover ACTIVE state. Requests use deterministic persisted IDs, validateOnly, billing eligibility, exact project identity, required permissions, a restricted custom-role definition, reviewed policy fingerprint and resource caps. Known local resources cover eventual listing lag. A global leased cloud-job lock bounds concurrent work; ambiguous requests retry the same resource, never a new ID. Google quota failures remain authoritative; no billing/quota bypass exists.

Add existing: label → exact URL → server alias → background validation → explicit result-bound confirmation → transactional registration. Existing Rules are verified, never rewritten. A new/unassigned database must also be empty (shallow key check); nonempty or duplicate canonical legacy identities require manual ownership review and are never silently recycled. Create: alias → label → billed-resource confirmation → durable job → official create → apply deny-all Rules only to that newly provisioned resource → verify → register. Failures retain diagnostics/jobs without an assignable instance. Retries are bounded to six background attempts; explicit owner retry resumes the same operation. Remote resources are not deleted on failure.

Architecture is backend-mediated. Direct-client Rules are exactly `{rules:{".read":false,".write":false}}`; nested overrides are refused. Verification checks Cloud identity/state, exact Rules, backend connectivity, and independent unauthenticated read/write denial. Real local emulator tests also deny anonymous and two authenticated client identities. Admin reads alone are never treated as Rules evidence. Actual live cloud checks were NOT run here.

Existing /firebase/status, /firebase/request-link and /firebase/approved-link contracts remain; status gains instance_state. Approval exposes only the authenticated customer's URL after eligibility and verified assignment checks. Approval is disclosure, not data authorization. /firebase/capabilities is an authenticated rollout guard. Android adds only status/request/approved-link controls in existing Settings; normal Firebase 403/503 does not clear a valid login. Older backends do not pass the capability guard. No management credentials/admin endpoints enter Android.

A separately disabled /firebase/preferences GET/PUT gateway demonstrates narrowly scoped backend-mediated access. It derives the database from the bearer account, checks approval/eligibility/verification/current project and Rules, and allows only theme/locale fields at one fixed path. No arbitrary database ID/path, cross-customer URL, SMS, monitoring, financial secrets or device collection is accepted. Each authorized device must independently complete existing password/Telegram OTP login; this work adds no collector, device enrollment or covert access. The gateway is off by default and is not required for URL-disclosure/pool management.

## Limits

No live Google resources, credentials or billing configuration were supplied. Live provisioning/IAM/Rules validation, workload identity bootstrap, native Android device testing and VPS installation remain owner steps. IAM inheritance from folders/orgs must be reviewed privately by the operator; project policy/role checks do not prove that no inherited grant exists. Firebase quotas/costs and supported regions must be confirmed in the owner's project. The independent full original website and child app sources remain unavailable; no fabricated replacement was introduced.
